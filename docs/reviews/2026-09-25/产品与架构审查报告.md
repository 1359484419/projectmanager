## 二、易用性（新用户视角走查）

到"一个团队跑起第一个迭代"共约 40 次点击，主流程全部可用。做得好的：写操作都有 toast、看板拖拽乐观更新、表单校验前置、空态文案带指向、中英切换无残留、助手确认卡三键齐全且执行后看板即时刷新。

P1（8 条，全部纳入本次修复）：

1. 注册后空概览没有任何"下一步"入口，顶栏「新建」在无项目时是死按钮。
2. 概览「去创建迭代」跳到规划页，而规划页无法创建迭代；看板/报表空态也把人送错页。
3. 普通成员看到完整管理员面板（新建/删除项目、邀请、改租户名、移出管理员），点了才报「resource not found」。
4. 「看板 / Board」被译成「仪表盘」，与「概览 / Dashboard」冲突，和 README、错误文案矛盾。
5. 移动端（390px）完全未适配：侧栏常驻 224px，标题竖排，看板四列横向滚动。
6. 未登录打开租户深链停在永久骨架屏，不跳登录。
7. 注册接口后端只校验非空：任意字符串邮箱、1 位密码都能注册。
8. 启动第二个迭代的确认框说"当前迭代将被关闭"，实际后端拒绝并抛英文错误。

P2/P3（16 条）：空态提示互相矛盾、头像永远显示「我」、品牌名与 Logo 不一致、接受邀请页不显示团队/角色、助手把内部工具名泄露给用户、快捷键不可发现、「0% 完成」与「已完成 1」并列、任务抽屉无迭代字段、快速创建行不能指派、后端英文错误直出、403/404 混用、日期格式随浏览器 locale、PAT 卡片无接入指引等。

## 三、完善度与设计完整性

做得好的：多租户隔离（拦截器 + Mapper 架构测试 + 404 语义）、乐观锁 409、自动轮转幂等补跑、助手侧 fail-closed 分级 + interrupt 审批 + checkpoint 幂等写 + 审计表，三套测试 Java 140 / Python 154 / 前端 60 全绿。

P0（3 条，本次修复）：

- **没有数据库备份**：只有 jar 备份，tasks/comments/activities 一次误删或磁盘故障不可恢复。→ 每日 `pg_dump -Fc` systemd timer，保留 14 天，恢复步骤写进 deploy/README。
- **RECORD「创建者私有」被 sprintId 绕过**：记录一旦挂进迭代，所有成员在看板能看到并拖拽。→ RECORD 强制 sprintId/assigneeId/epicId 为空；迭代/Epic 查询过滤 RECORD；补集成测试。
- **权限矩阵只覆盖 4 类管理动作**：任何成员可启动/关闭/删除迭代、增删 Epic、改任何人的任务。→ 先定义矩阵（迭代启停删除、Epic 删除、项目设置、邀请/成员 = ADMIN；任务/评论/子任务/Epic 创建编辑 = 全员；删除任务 = 创建者或 ADMIN），再抽 `@RequireRole` 注解 + 拦截器 + 架构测试枚举全部写端点。

P1（5 条）：框架级异常全部 500（坏 JSON、缺参数、非法枚举）；无密码策略/邮箱未归一化/无登录限流；无登出吊销与找回密码；公网明文 HTTP；缺优先级/截止日期/评论编辑。其中前两条本次修复，其余进路线图。

设计决策修订：角色不足的响应从"404 不暴露"改为 **403 FORBIDDEN + 中文说明**。理由：调用方已是租户成员，资源存在性不是秘密，而 404 让用户以为系统坏了；跨租户仍保持 404。

## 五、多轮语义测试（真模型实跑）

临时租户 3 成员、2 项目、10 条种子任务，经 Java 反代跑 58 个场景（47 主场景 + 10 复测 + 1 手工续跑）。完整记录：`多轮语义测试记录.md`，可复跑脚本 `run_scenarios.py`。

| 判定 | 数量 |
|------|------|
| 通过 | 46 |
| 追问合理 | 4 |
| 语义偏差 | 4 |
| 工具误用 | 2 |
| 幻觉 | 2 |
| 通过率 | 86% |

harness 层（分级/确认卡/拒绝不重发/409 不重试/注入隔离/多义追问）未发现绕过。失败集中在三处，全部纳入本次修复：

1. **edit 决策上下文缺失（2/2 复现，最严重）**：用户在确认卡改了参数并执行成功后，tool 消息没告诉模型"参数已被用户改过"，模型要么重发原值的卡，要么谎称未执行。→ act 层在 edit 结果前置固定模板"用户已把参数改为 …并执行，这是最终意图"。
2. **否定型幻觉（1/4 复现）**：未调任何工具却回复"KB-9 没有找到（NOT_FOUND）"。→ 提示词规则扩展为"未调工具既不得说已完成、也不得说不存在/失败"，并加观测打点。
3. **无端创建副作用**：多轮指代链里模型自作主张 create_subtask(占位) 再出 delete_subtask 卡。→ type 默认 TASK 消除追问抖动；规则"每个创建调用必须对应用户明确要求"。

P2：「我在待办里有哪些任务」被解析为全项目 backlog（忽略"我"）；get_task 透出内部数字 id 被念给用户；close_sprint 卡片标题显示「current」而非真实迭代名；注入标题被模型改写；「上一个」指代偏差；回复夹带内部术语；create_sprint 描述与后端缺省不符；真模型冒烟只有 5 条不覆盖这些失败。

## 六、MCP 生态

实测 6 个工具端到端可用，PAT 鉴权与租户隔离扎实，SKILL.md 承诺的三条流程能走通。问题：

- **P1 线上信息泄露**：协议层 400（缺 session、Accept 不对、未知 session）把 Java 完整堆栈序列化返回给客户端，任何持 PAT 的成员可触发。
- **P1 静默丢字段**：`create_tasks` 的 tasks 项无 `additionalProperties:false`，外部模型习惯性写 `assignee` 会被吞掉，任务挂到自己名下且无警告。
- **P1 日报数据面不足**：`list_my_tasks` 只有 5 个字段，无 doneAt/描述/backlog/跨项目，SKILL.md 的日报模板只能靠猜。
- P2：错误不定位资源、工具无 title/annotations/outputSchema/instructions、有状态会话未绑身份且重启即失效、SKILL.md 与实际命令不一致、无 resources/prompts。

**架构决策：统一到 Python 工具目录，Java `/mcp` 改为 PAT 认证后直通反代。** 探针已证明 mcp 2.x `MCPServer` 以无状态 Streamable HTTP 挂在 FastAPI 下、工具内可读注入头、PAT 直接回调 Java REST 全链路零后端改动。评审提出的 8 个前提逐条落实：

| 前提 | 处理 |
|------|------|
| mcp 2.x API 变化 | 锁 `mcp>=2.2,<3`，用 `MCPServer`，客户端 `streamable_http_client(http_client=…)` |
| 现有助手反代不能复用 | 新写 `McpProxyController`：只做 PAT 校验 + 注入 X-PM-* + 直通 POST，无状态、JSON 响应 |
| 与 LLM/agent DB 初始化耦合 | MCP 子应用独立 lifespan，只依赖 PmClient；`/health` 分开报告 |
| 确认机制不通用 | 外部 agent 无确认卡：L3 工具 `confirm:true` 必填 + `destructiveHint` + `dry_run` 预览三者叠加；首版不开放 delete_*/成员管理 |
| 批量创建非事务 | `create_tasks` 别名返回 `created[]` + `failed[]`，逐条明确 |
| 输出泄内部 id | MCP 输出统一 `to_wire` 清洗：只出展示号、名称、状态 |
| 上下文成本 | 只暴露精选 14 个（schema ≤2.5K tokens），33 个全量留给面板助手 |
| 旧客户端兼容 | 6 个旧工具名与参数形状作为别名保留（projectKey/taskSeq/target） |

目标工具集（14 个）：读 `list_projects / get_project_overview / list_my_work / get_task / search_tasks / get_board / list_members`；写 `create_tasks（含 dry_run、assignee、unassigned）/ add_comment / create_subtask / update_task_status / update_task / move_task_to_sprint`；L3 `close_sprint / start_sprint`。资源 `pm://projects`、`pm://projects/{key}/sprints/current`、`pm://me/work`；提示词模板 `daily_report / weekly_report / plan_from_notes`。
